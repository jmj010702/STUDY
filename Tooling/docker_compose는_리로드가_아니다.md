## `docker compose up -d`는 설정 리로드가 아니다

### 문제 배경

`prometheus.yml`에 job 3개를 추가한 뒤 `docker compose up -d`를 재실행했더니 **반영됐다.**

그런데 **Prometheus는 설정 파일 변경을 자동 감지하지 않는다.**
결과는 맞는데 원리가 설명되지 않아서 무엇이 일어났는지 추적했다.

### 문제 — 결과는 맞았지만 메커니즘이 달랐다

```
Created:      2026-08-15T12:35:15   ← 첫 기동(12:24 이전)과 다른 시각
RestartCount: 0                      ← 재시작이 아니라 신규 생성
설정 로드 로그: 1회                   ← 기동 시 로드가 전부
```

`up -d`는 compose 정의와 실행 중인 컨테이너를 비교해 **필요하면 지우고 새로 만든다.**
**리로드가 아니라 컨테이너 재생성이었다.** 결과는 같아 보여도 다른 일이다.

### 검증 — SIGHUP이 정석

```bash
docker kill -s HUP prometheus
```

| | 전 | 후 |
|---|---|---|
| `StartedAt` | 12:35:16 | **불변** |
| **PID** | **67984** | **67984 (동일)** |
| `RestartCount` | 0 | 0 |
| 설정 로드 횟수 | 1 | **2** |
| `count(up)` | — | **5 (유지)** |

**PID가 같다 = 프로세스가 죽지 않았다.**
`docker kill -s HUP`은 컨테이너를 죽이는 게 아니라 **시그널을 보내는** 명령이다.
(`kill`이라는 이름 때문에 오해하기 쉽다.)

### 방법별 비교

| 방법 | 프로세스 | 수집 |
|---|---|---|
| **`docker kill -s HUP`** | **유지** | **무중단** |
| `docker compose up -d` | 재생성 | 끊김 |
| `docker compose restart` | 죽었다 뜸 | 끊김 |
| `POST /-/reload` | 유지 | compose에 `--web.enable-lifecycle` 필요 |

### 부수 함정 — 리로드 직후에는 옛 시계열과 새 시계열이 공존한다

리로드 직후 `up`을 조회했더니 **삭제한 job들이 그대로 보였다.**
설정은 반영됐는데(로그 확인) 아직 새 스크레이프가 돌지 않았고,
**사라진 target의 마지막 샘플이 최대 5분간 instant query에 남아 있기** 때문이다.

**리로드 후에는 최소 한 번의 `scrape_interval`(15초)을 기다린 뒤 확인해야 한다.**

대기 조건을 만들 때도 주의가 필요하다 — `up{job="hr-service"}`가 나올 때까지 기다리게 했는데,
**삭제 예정인 옛 static job도 이름이 `hr-service`라 즉시 통과해버렸다.**

### 배운 점

> **"결과가 맞으면 과정도 맞다"고 넘기면 메커니즘을 잘못 배운다.**
> 지금은 데이터가 적어 재생성 비용이 안 보이지만, 시계열이 쌓이면 실제 비용이 된다.
