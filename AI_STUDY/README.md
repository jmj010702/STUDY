## 기술 스택 (기준 시점: 2026)

| 구분 | 선택 |
|---|---|
| 언어 | Python 3.12 |
| 프레임워크 | LangChain v1.x (LCEL), 다단계는 LangGraph |
| LLM | Claude(`langchain-anthropic`) ↔ 로컬 Ollama 전환 가능 |
| 임베딩/벡터DB | ChromaDB (로컬), `RecursiveCharacterTextSplitter` (청크 1000자 / 오버랩 200자) |
| UI | Streamlit (프로토타입) |

**작업이 단순하면 RAG 체인, 도구·다단계가 필요할 때만 LangGraph 에이전트로 승격.**

## 보안 원칙 (처음부터 못 박은 것)

- 검색된 문서는 **'데이터'로만 취급**하고 그 안의 지시문은 따르지 않는다 (간접 프롬프트 인젝션 방어)
- 검색 컨텍스트는 `<context></context>` 태그로 감싸 시스템 프롬프트와 분리
- ERP 조회는 **읽기 전용(SELECT)만** 허용, 쓰기/삭제 차단

## RAG 기본 개념 정리

**청크로 쪼개는 이유**

| 이유 | 내용 |
|---|---|
| 검색 정확도 | 50p 문서를 통째로 두면 질문해도 전체가 통으로 걸려 핵심이 묻힌다 |
| 입력 한도·비용 | 관련 4개만 넣으면 싸고 빠르다 |
| 임베딩 품질 | 짧고 한 주제일수록 벡터가 또렷하다 |

**왜 겹쳐서(오버랩 200자) 자르나**
1000자에서 칼같이 자르면 핵심 정보("15일")가 경계에서 끊길 수 있다.
200자 겹쳐 자르면 경계가 양쪽 청크에 다 들어간다.

**자른 걸 다시 합치면 도로아미타불 아닌가**
아니다. **자르기 → 고르기 → 합치기** 순서이고, 가운데 "고르기(검색)" 덕분에
50개 중 **관련 4개만** 합쳐진다. 원본 복원이 아니라 알짜 추림.

**vectorstore vs retriever**

| | 역할 |
|---|---|
| vectorstore | ChromaDB **만들기/저장**(가끔) + 검색도 가능(`similarity_search`) |
| retriever | 그 검색을 **체인에 꽂는 표준 부품**으로 감싼 것 |

검색 엔진은 하나, 부르는 방법이 둘이다.

**splitter vs retriever**
splitter는 문서를 **다 자른다**(질문 없음). retriever는 질문에 맞는 걸 **찾는다**(질문 있음).
자르기 vs 찾기, 정반대 단계.
