## 404가 500으로 둔갑해 오류율을 오염시킨다

### 문제 배경

RED 지표의 E(오류율)를 만들려고 5xx 메트릭을 살펴보던 중이었다.

### 문제

```
http_server_requests_seconds_count{uri="/**", status="500", outcome="SERVER_ERROR"}  10
```

`uri="/**"`는 **매칭되는 핸들러가 없는 요청**을 뜻한다.
정상이라면 404여야 하는데 **500으로 찍혀 있다.**

### 원인 분석

경로가 없어 정적 리소스 조회로 흘렀고, `GlobalExceptionHandler`가
`NoResourceFoundException`을 잡아 **500으로 변환**하고 있었다.

```json
{"detail":"NoResourceFoundException: No static resource actuator/health."}
```

전역 예외 핸들러가 "모르는 예외는 전부 500"으로 처리하는 흔한 구조인데,
스프링이 던지는 **"리소스 없음" 예외까지 서버 오류로 뭉뚱그린 것**이다.

### 왜 심각한가 — 지표 설계에 직접 영향

```
RED의 E(오류율) = rate(5xx) / rate(전체)
                       ↑
        여기에 "누가 주소를 오타로 친 것"이 섞인다
```

**오탐의 원천**이다.
크롤러나 스캐너가 없는 경로를 두드리면 5xx 오류율이 치솟고, **알림이 울리지만 서버는 멀쩡하다.**
그리고 **오탐이 반복되면 알림 자체가 무시된다** — 관측 체계가 죽는 가장 흔한 경로다.

### 해결 방향

두 갈래이고, 각각 성격이 다르다.

| 방법 | 내용 | 성격 |
|---|---|---|
| 쿼리에서 제외 | 오류율 쿼리에서 `uri="/**"`를 뺀다 | 관측 쪽에서만 처리. 앱은 안 건드림 |
| 예외 처리 수정 | `NoResourceFoundException`을 404로 반환 | 근본 해결이지만 **앱 동작 변경**이라 팀 합의 필요 |

**어느 쪽이든 "왜 제외했는지"를 근거로 남겨야 한다.**
지표에서 뭔가를 빼는 결정은 나중에 "왜 이 수치가 실제와 다르지?"의 원인이 되기 때문에,
제외 사실 자체를 지표와 함께 보여줘야 한다.

### 배운 점

> **오류율은 "5xx를 세면 되는" 단순한 지표가 아니다.**
> 무엇이 5xx로 집계되는지는 **앱의 예외 처리 코드가 결정**한다.
> 지표를 만들기 전에 **그 숫자가 실제로 무엇을 세고 있는지**부터 확인해야 한다.
