## Service Discovery를 쓰면 죽은 대상이 목록에서 사라진다

### 문제 배경

Prometheus 수집 대상을 `static_configs`에서 `eureka_sd_configs`(Service Discovery)로 전환했다.
포트가 바뀔 때마다 설정 파일을 고치는 운영 부담을 없애는 게 목적이었다.

### 문제

전환 후 api-gateway를 재시작하며 관찰했다.
`up` 값이 0이 되는 것까지는 예상했으나, **그 뒤에 시계열이 통째로 사라지는 것**은 예상하지 못했다.

```
03:06:00  up=1   전체 target 6개
03:06:15  up=0                      ← 스크레이프 실패
03:07:00  up=0
03:07:30  (up 값 없음)  target 5개  ← ★ target 자체가 삭제됨
03:08:00  (up 값 없음)  target 5개
03:08:30  up=1          target 6개  ← 복귀
```

### 원인 분석

```
① 앱 정지
      ↓
② Prometheus 스크레이프 실패 → up=0 기록
      ↓
③ Eureka가 인스턴스를 레지스트리에서 제거
      ↓
④ Prometheus SD가 목록 재조회 → 해당 인스턴스 없음
      ↓
⑤ target 삭제 → up 시계열이 사라짐
```

### 왜 심각한가 — 알림이 반대로 동작한다

```
알림 규칙: up == 0 이면 알려라

앱 정지 → 잠시 up=0 → 알림 조건 만족 → 울림
        → target 소멸 → 평가할 시계열 없음 → 조건 미충족 → 알림 해제
        → 앱은 여전히 죽어 있는데 알림은 조용하다
```

**앱이 오래 죽어 있을수록 알림이 조용해진다.**
"없는 시계열은 `0`이 아니라 결과에서 빠진다" — 즉 **침묵과 정상이 구분되지 않는다**는 문제의 실물이다.

### 이것은 SD 도입의 대가다

| | `static_configs` | `eureka_sd_configs` |
|---|---|---|
| 앱 정지 시 | **target이 남아 `up=0` 유지** | `up=0` 잠시 → **target 소멸** |
| `up == 0` 알림 | 계속 감지됨 | **일정 시간 후 무력화** |
| 포트 변경 대응 | 수동 수정 필요 | 자동 |
| 앱 재시작 시 시계열 | `instance`가 바뀌어 **끊김** | instanceId 유지되어 **이어짐** |

**SD가 일방적으로 우월한 것이 아니다.** 운영 부담을 줄인 대신 "사라짐"의 감지가 어려워졌다.

### 해결 방향

- **`absent()`** — 시계열이 존재하지 않는 것 자체를 조건으로 삼는 함수
- Eureka에 등록된 앱 목록과 실제 target 수를 비교하는 별도 지표
- **어느 쪽이든 "없음"을 능동적으로 감지해야 한다.** `up == 0`만으로는 부족하다

### 미확인 — 재실험 필요

> 이번 관찰은 **재시작이 2회 겹쳐 있었다**(counter가 `1455 → 6`, `6 → 1`로 두 번 리셋된 것으로 확인).
> 따라서 **"정지 후 몇 초 만에 target이 사라지는가"는 특정할 수 없다.**
>
> 타이밍은 `eureka.instance.lease-expiration-duration-in-seconds`(Eureka 만료)와
> `refresh_interval: 30s`(SD 갱신 주기)가 겹쳐 결정된다.
> **`absent()`를 설계하려면 깨끗한 단일 재시작으로 다시 측정해야 한다.**

### 배운 점

> 도구를 도입할 때 **얻는 것만 보고 잃는 것을 안 보면 안 된다.**
> SD는 "포트 관리를 자동화"해주지만 그 대가로 "죽었다는 신호"를 가져간다.
> 트레이드오프를 알고 쓰면 대응(`absent()`)이 가능하고, 모르고 쓰면 **알림이 조용한 걸 정상으로 착각한다.**
