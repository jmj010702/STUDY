# histogram_quantile() — 분포에서 백분위를 되찾는다

> **histogram = 측정값 하나하나를 버리고, 미리 정해둔 칸에 몇 개가 떨어졌는지만 세는 것.**
> 백분위는 그 표에서 **계산해내는 추정치**이지 저장된 값이 아니다.

## 1. 무엇이 저장되고 무엇이 버려지나

hr-service가 요청을 28번 받았을 때 남는 것:

```
개별 저장이라면:  0.041, 0.052, 0.049, 0.038, 0.057, ...  (28개 숫자)
                     ↓ 버린다
histogram:        le=0.0503 → 18건 / le=0.0559 → 23건 / le=0.0615 → 28건
```

**개별 값을 다 들고 있으면 정확하지만 비싸다.** 요청 100만 건이면 숫자 100만 개다.
histogram은 "몇 번째 칸인가"만 세서 수십 개로 압축한다. **정확도를 팔아 비용을 산다.**

동전에 비유하면 — 동전마다 제조년도를 기록하는 대신 500원통·100원통·10원통에 넣고 통마다 몇 개인지만 세는 것. 각 동전이 몇 년산인지는 모르지만 개수는 바로 안다.

## 2. `le`는 시간 경계이고, 누적이다

`le` = **l**ess than or **e**qual (이하)

```
le="0.050331646"  값 18   →  "0.0503초 이하로 끝난 요청이 18건"
```

**그 칸에만 18건이 아니라 그 칸까지 합쳐서 18건**이다.
그래서 값이 커지기만 하고 `+Inf`는 전체 개수와 같아진다.

### ⚠️ `le`와 백분위의 `95`는 서로 다른 축이다

| | `le` | p95의 `95` |
|---|---|---|
| 단위 | **초 (시간)** | **퍼센트 (비율)** |
| `le=0.95`의 뜻 | "0.95초 이하로 끝난 건수" | — |
| p95의 뜻 | — | "95%가 그 안에 들어오는 **시간**은?" |

**`p95 = le 0.95`가 아니다.** 하나는 시간, 하나는 비율이다.

참고로 p99가 200ms라면 → 요청의 99%는 200ms 이하로 끝났고, **1%는 200ms보다 오래 걸렸다.**

## 3. 버킷 개수는 Micrometer가 정한다

관측된 `le` 값:
```
0.001  0.001048576  0.001398101  ...  28.633115306  30.0  +Inf     (총 69개)
       ↑ 2^20 나노초. 사람이 고른 반올림 값이 아니다
```

Micrometer는 **4의 거듭제곱 기반 고정 후보 집합(160개 이상)**을 갖고 있고,
`minimumExpectedValue` ~ `maximumExpectedValue` 범위로 **잘라낸다**(`PercentileHistogramBuckets`).
범위가 `0.001~30.0`이라 69개가 남았다. 설정한 적이 없으므로 그게 기본값이다.

> **라이브러리마다 기본 버킷이 다르다.** Prometheus 공식 클라이언트는 사람이 고른
> `.005 .01 .025 .05 .1 .25 .5 1 2.5 5 10` 약 11개인데 Micrometer는 69개다.
> **같은 "histogram을 켠다"의 비용이 스택마다 6배 이상 차이난다.**
>
> **`maximum-expected-value`를 줄이면 버킷이 준다** — 비용 조절 손잡이가 여기다.

## 4. p95를 뽑는 과정 — 손으로 계산해서 함수와 대조

```
1) 전체 개수를 본다              →  +Inf = 28건
2) 95% 지점                      →  0.95 × 28 = 26.6번째
3) 표를 훑어 26.6을 처음 넘는 칸  →  le=0.0559(23건) ~ le=0.0615(28건) 사이
4) 그 칸 안에서 비례 계산(선형 보간)
      (26.6-23) / (28-23) = 0.72
      0.055924051 + (0.061516456 - 0.055924051) × 0.72 = 0.059950582600
```

```
histogram_quantile(0.95, ...)  →  0.059950582599999996     ← 일치
```

**뽑히는 값의 단위는 "초"다.** 그리고 `0.0599`는 **69개 `le` 어디에도 없는 숫자**다 — 칸과 칸 **사이**를 추정한 값이라서.

> **그래서 p95는 추정치다.** 진짜 값은 `0.0559 ~ 0.0615` 사이 어딘가이고,
> 그 구간 5건이 실제로 어떻게 흩어졌는지는 버렸다. 함수는 **균등 분포를 가정**하고 비례 계산할 뿐이다.
> **버킷이 촘촘할수록 구간이 좁아져 추정이 정확해진다.**

> ⚠️ **두 조회를 같은 시각으로 고정해야 한다.** 버킷을 조회한 뒤 함수를 실행하면
> 그 사이 스크레이프가 돌아 counter가 늘어 값이 안 맞는다(실제로 24건 → 28건으로 늘어 손계산이 어긋났다).
> `time=` 파라미터로 고정하면 정확히 일치한다.

## 5. 실전 쿼리 — 배운 것이 전부 만난다

```promql
histogram_quantile(0.95, sum(rate(http_server_requests_seconds_bucket[5m])) by (le))
└────────⑤────────┘  └─④─┘└─③─┘└──────────②──────────┘└─①─┘
```

| | 단계 | 타입 | 줄 수 | 무슨 일이 |
|---|---|---|---|---|
| ① | `..._bucket` | vector | **276** | 4 job × 69 le |
| ② | `[5m]` | **matrix** | 276 | 각 줄이 값 1개 → **20개의 나열**로 |
| ③ | `rate(...)` | vector | 276 | **다시 값 1개씩** (초당 증가율) |
| ④ | `sum(...) by (le)` | vector | **69** | `le`만 남기고 나머지 라벨 병합 |
| ⑤ | `histogram_quantile` | vector | **1** | 69개 칸에서 값 하나 |

**276 → 69 → 1.** 각 단계가 무엇을 없애는지가 줄 수로 보인다.

검산:
```
le=0.050331646  →  0.26316     "초당 0.263건이 50.3ms 이하로 끝났다"
+Inf            →  0.26667     4서비스 × (15초에 1건) = 4÷15 = 0.26667  ✅
```

## 6. ⚠️ `by (le)`는 선택이 아니라 필수다

```promql
histogram_quantile(0.95, sum(rate(...[5m])))     # by (le) 없음
```
```json
{"status":"success", "result":[],
 "warnings":["bucket label \"le\" is missing or has a malformed value of \"\""]}
```

`histogram_quantile()`은 **`le` 라벨을 보고 칸의 경계를 안다.**
`sum()`은 지정하지 않은 라벨을 전부 버리므로, `le`까지 날아가면 계산할 근거가 없다.

**에러가 아니라 `"status":"success"` + 빈 결과 + 경고다.**
브라우저 UI나 `curl` 출력에서 **`warnings` 필드를 습관적으로 확인할 것.**

**`rate`는 `sum` 안쪽**이어야 한다 — counter 리셋 보정이 깨지고, 타입 규칙상으로도 강제된다.

## 7. `by`에 무엇을 넣느냐가 "어느 단위로 볼 것인가"다

| 쿼리 | 결과 | 의미 |
|---|---|---|
| `by (le)` | 1줄 | 전체 통합 p95 |
| `by (le, job)` | **4줄** | **서비스별 p95** |

```
api-gateway            0.0071초
search-service         0.0253초
collaboration-service  0.0338초
hr-service             0.0499초
```

**`le`는 함수가 요구해서 반드시 넣고, 그 외에 넣는 라벨이 쪼개는 기준이 된다.**
`uri`별로 보고 싶으면 `by (le, uri)`.

이것이 **"histogram은 합칠 수 있다"**의 실물이다. 버킷은 개수라서 서비스 4개 것을 더해도 말이 된다.
summary였다면 각자 계산해버린 p95를 더하는 꼴이라 무의미하다.

## 8. 평균으로는 안 보이는 것

| | hr-service |
|---|---|
| 평균 (`sum`/`count`) | 0.0488초 |
| **p95** | **0.0499초** |

평균은 느린 요청을 빠른 요청이 희석시켜 감춘다.
**"평균은 괜찮은데 일부 사용자는 느리다"를 잡으려면 백분위가 필요하다.**
RED의 D를 평균이 아니라 p95로 보는 이유.
