# PromQL

## 1. 용어 — target / job / instance

```
http://      192.168.45.118:65201      /actuator/prometheus
schema       __address__ (target)      __metrics_path__
```

| 용어 | 뜻 |
|---|---|
| **target** | Prometheus가 긁는 대상 하나 == 주소 하나(`IP:PORT`). 스크레이프 주기(15초)마다 이 URL에 GET을 보낸다 |
| **job** | target들의 묶음 이름. ex) `hr-service`. job 하나 안에 target이 여러 개일 수 있다 |
| **instance** | 그 타겟을 식별하는 라벨. ex) `DESKTOP-5TOO5J4:hr-service:0` |

**job과 instance는 묻는 게 다르다.** job은 "어느 서비스냐", instance는 "그 중 몇 번째 놈이냐".

## 2. `up` — 첫 쿼리

```promql
up
```
> `up`이라는 이름을 가진 시계열을 전부, 각각의 최근 값 하나씩 가져와라

```
up{job="hr-service", instance="DESKTOP-5TOO5J4:hr-service:0"}   0
```
> job이라는 꼬리표에 `hr-service`가, instance라는 꼬리표에 `DESKTOP-...`이 적혀 있는 `up` 시계열의 최근 값은 0이다.

### `up`은 앱이 만드는 메트릭이 아니다

앱은 `up`을 내보내지 않는다. **Prometheus가 스크레이프를 시도하고 그 결과를 스스로 기록한 것**이다. 그래서 앱이 완전히 죽어도 `up=0`이 남는다.

### `up=0`은 원인을 구분해주지 않는다

앱 다운 / 네트워크 차단 / 포트 변경 / 방화벽 — 전부 `up=0`이다. **"긁지 못했다"는 사실만 말한다.**

### 제3의 상태

`up=1`(성공), `up=0`(실패) 외에 **"시계열이 아예 없음"**이 있다. Service Discovery를 쓰면 죽은 대상이 목록에서 빠지면서 이 상태가 된다 → [SD 전환 후 죽은 대상이 사라진다](트러블슈팅/SD전환후_죽은대상이_사라진다.md)

## 3. 라벨 필터

```promql
up{job="hr-service"}
```

| 문법 | 의미 |
|---|---|
| `{}` | 괄호 안 조건에 맞는 것만 |
| `=` | 정확히 같다 |
| `=~` | 정규식에 맞다 |
| `!~` | 정규식에 안 맞다 |
| `,` | **and** (or가 아니다) |
| `\|` | or — 반드시 **따옴표 안**에서 |

**규칙 두 가지**
- 라벨 이름에는 따옴표를 쓰지 않는다. `"job"="hr-service"` ✗
- 값에는 따옴표가 필수다.

### ⚠️ 정규식은 부분 일치가 아니라 **전체 일치**다

```
status=~"2"     →  0개    ← 200, 204에 '2'가 들어있는데도
status=~"2.*"   →  9개
status=~"2.."   →  9개
```

`status=~"5"`로 5xx를 잡으려 하면 **에러 없이 빈 결과**가 나와서 오류율이 0%로 보인다.
HTTP 상태코드는 항상 세 자리이므로 **`5..`가 `5.*`보다 의도를 정확히 표현한다.**

상세: [PromQL 함정 모음](트러블슈팅/PromQL_함정_모음.md)

## 4. 집계 — `sum` / `by` / `without`

```promql
sum(jvm_memory_used_bytes) by (job)
```

- `sum()` — 지정하지 않은 라벨을 **전부 버린다**
- `by (라벨)` — **남길** 라벨을 지정. DB의 `GROUP BY`와 같은 느낌
- `without (라벨)` — **버릴** 라벨을 지정

`by`의 동작 순서:
```
by (exam) → ① exam 값이 같은 것끼리 바구니에 담고
            ② 바구니마다 sum을 하고
            ③ exam 라벨만 결과에 남긴다
```

라벨을 여러 개 쓸 때는 `by (code, exam)`처럼 쉼표로 구분한다.

| 함수 | 묻는 것 |
|---|---|
| `sum` | 얼마나 **많은가** |
| `count` | 몇 **종류**인가 |

**필터는 집계보다 먼저 걸린다.**

```promql
sum(prometheus_http_requests_total{code="400"}) by (handler)
```
> 전체 http 요청 메트릭 중 code가 400인 시계열을, handler(요청 경로)마다 그룹화해서 합산

## 5. instant vector와 range vector — 타입을 맞추는 게임

### 왜 counter는 그냥 읽으면 안 되나

counter는 누적값이라 "1523건"이 많은지 적은지 모른다. 알고 싶은 건 **변화**인데, **값 하나로는 변화를 계산할 수 없다.**

### `[5m]` — 타입을 바꾸는 스위치

| 표기 | 타입 | 내용 |
|---|---|---|
| `metric{...}` | **instant vector** | 시계열마다 **값 1개** (최근값) |
| `metric{...}[5m]` | **range vector** | 시계열마다 **값 여러 개** (5분치 나열) |

**`sum`은 instant vector만 받는다. range vector는 못 받는다.**
그래서 `sum(metric[5m])`은 에러고, `sum(rate(metric[5m]))`이 맞다 — `rate()`가 range를 다시 instant로 되돌리기 때문.

```
..._bucket{le="0.0615"}       →  값 1개:  171
                       [5m]   →  값 20개: 152 153 154 ... 171   (15초 간격)
rate(              [5m])      →  값 1개:  0.0667
```

**`[5m]`이 1개를 20개로 늘렸고, `rate()`가 값 하나로 되돌렸다.**
20개짜리(range vector)는 그래프에 선을 못 긋고 `sum()`에도 못 넣는다.

> **PromQL은 가장 안쪽 괄호부터 읽는다.**

## 6. `rate` / `increase` / `irate`

| 함수 | 계산 | 단위 |
|---|---|---|
| `rate(c[5m])` | (끝값 - 시작값) ÷ 구간초 | **초당** 증가율 |
| `increase(c[5m])` | 끝값 - 시작값 | 구간 동안 **총 증가량** |
| `irate(c[5m])` | 마지막 **두 점**만 본다 | 순간 변화율 |

### `rate()`는 집계보다 **먼저** 와야 한다

```promql
sum(rate(metric[5m]))   ✅
rate(sum(metric)[5m])   ❌
```

`sum`을 먼저 하면 **counter 리셋 보정이 깨진다.** 앱이 재시작해 counter가 0으로 떨어졌을 때, `rate()`는 개별 시계열 단위로 그걸 알아채고 보정하는데 이미 합쳐버리면 그 정보가 사라진다. 타입 규칙상으로도 강제된다.

### `increase()`가 정수로 안 나오는 이유

구간 경계가 스크레이프 시점과 정확히 안 맞아서 **외삽(extrapolation)**을 한다. `10.0000001` 같은 값이 나오는 게 정상이다.

### 창 길이를 바꾸면 무엇이 달라지나

짧으면 민감하고 노이즈가 많다. 길면 부드럽지만 짧은 스파이크를 뭉갠다. **최소 스크레이프 간격의 4배 이상**을 권장한다(15초 주기면 1m 이상).

### 자주 쓰는 접미사

| 이름 | 뜻 |
|---|---|
| `..._seconds_count` | **몇 건** 왔나 |
| `..._seconds_sum` | 총 **몇 초** 걸렸나 |
| `..._seconds_max` | 가장 오래 걸린 게 몇 초 |
| `..._seconds_bucket` | **구간별로 몇 건** |

## 7. 없는 시계열은 `0`이 아니라 결과에서 빠진다

조건에 맞는 시계열이 하나도 없으면 **`0`이 반환되는 게 아니라 결과 자체가 비어서** 나온다.

```
오류가 0건인 상태  →  결과 없음
쿼리가 잘못된 상태  →  결과 없음
앱이 죽은 상태     →  (SD면) 결과 없음
```

**셋이 구분되지 않는다.** 이게 "침묵과 정상이 구분되지 않는다"는 문제다.

`vector(0)`으로 채우는 방법이 있지만 **항상 채우면 안 된다** — 진짜 침묵까지 0(정상)으로 덮어버리기 때문. "데이터가 없는 것"과 "값이 0인 것"이 다른 의미인지 매번 판단해야 한다.

---

## 8. 시계열은 라벨 조합으로 식별된다

이름이 같아도 **라벨이 하나라도 다르면 다른 시계열**이다.

```
http_server_requests_seconds_count{job="hr", uri="/a", status="200"}   ← 다른 시계열
http_server_requests_seconds_count{job="hr", uri="/a", status="500"}   ← 다른 시계열
```

라벨 값의 종류가 늘어나면 시계열이 곱셈으로 폭발한다(카디널리티 문제). 사용자 ID 같은 걸 라벨로 넣으면 안 되는 이유.

## 9. RED와 USE — 무엇을 볼 것인가

### RED — 요청 기반 서비스를 보는 세 가지

| | 뜻 | 쿼리 형태 |
|---|---|---|
| **R**ate | 초당 요청 수 — 얼마나 오고 있나 | `sum(rate(..._count[5m]))` |
| **E**rrors | 실패한 요청의 수(율) — 얼마나 실패하나 | `sum(rate(..._count{status=~"5.."}[5m])) / sum(rate(..._count[5m]))` |
| **D**uration | 응답 시간의 분포 — 얼마나 느린가 | `histogram_quantile(0.95, sum(rate(..._bucket[5m])) by (le))` |

**D만 전제가 따로 있다** — histogram 버킷이 켜져 있어야 한다. R과 E는 `count`만으로 되지만 D는 `bucket`이 필요하다.

**E에는 이미 알려진 함정이 있다** — 없는 경로 요청이 500으로 집계되면 오류율이 오염된다. → [404가 500으로 둔갑](트러블슈팅/404가_500으로_둔갑.md)

### RED vs USE

| | RED | USE |
|---|---|---|
| 대상 | 서비스 / 요청 | 자원 (CPU, 메모리, 디스크) |
| 관점 | **사용자(UX)가 좋은가** | **서버가 좋은가** |
| PeopleCore 기준 | `http_server_requests_*` | `jvm_memory_used_bytes` |

**둘 다 필요하다.** 서버 자원이 여유로워도 사용자가 느릴 수 있고, 반대도 가능하다.
